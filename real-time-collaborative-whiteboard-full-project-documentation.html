1. Software Requirements Specification (SRS)

Problem Statement

Remote teams lack a unified, real-time canvas for visual collaboration. Existing tools are either too expensive, don't work offline, or provide no version history. CollabBoard solves this with an open-source, self-hostable solution.

Objectives

  • Enable simultaneous multi-user drawing with sub-100ms latency
  • Support offline editing with automatic reconnect & merge
  • Provide full version history with restore capability
  • Implement role-based access control (Owner / Editor / Viewer)
  • Deliver a responsive, accessible UI

7. Offline Synchronisation Algorithm

How It Works

  1. Detection: navigator.onLine + window online/offline events monitored by useNetworkStatus hook.
  2. Queuing: When offline, every DrawOperation is stored in IndexedDB (whiteboard_offline DB, pending_ops store) with a queuedAt timestamp.
  3. Reconnect detection: useOfflineSync hook listens for the browser's online event.
  4. Replay: Pending ops are sorted by queuedAt ascending, then re-emitted through Socket.IO with a 30 ms delay between each to avoid flooding.
  5. Cleanup: Each op is deleted from IndexedDB immediately after successful emission.
  6. Conflict resolution: Last-write-wins via timestamp. Vector clocks track causality across sessions.
OFFLINE QUEUE FLOW
─────────────────
User draws → isOnline?
    YES → emitDrawOperation(socket)
    NO  → enqueueOperation(IndexedDB)

browser fires 'online' event
→ getPendingOperations() [sorted by queuedAt ASC]
→ for each op:
    socket.emit('draw:operation', op)
    await 30ms
    removeOperation(op.id)
→ log "Sync complete"

8. Versioning Algorithm

Snapshot Strategy

  • Manual save: User clicks "Save now" in VersionPanel → POST /api/versions/:roomId with full Fabric.js JSON + label.
  • Auto-save trigger: Server counts ops per room in Redis. Every 30 ops, the frontend owner is signalled to push the full canvas.
  • Undo/Redo: Client-side only — a circular buffer of JSON snapshots (max 50 entries, O(1) push/pop).
  • Restore: POST /api/versions/:roomId/:vId/restore — server replaces room.canvasData and emits a room:canvas_saved event so all connected clients reload.
  • Version numbering: Sequential integer per room, determined atomically by querying MAX(versionNumber) before insert.

9. Conflict Resolution Strategy

ScenarioStrategy
Two users move the same object simultaneouslyLast-Write-Wins (LWW) based on op.timestamp. The op with the higher timestamp wins and overwrites the object state.
User A deletes, User B modifies the same objectDelete wins. The modify op is silently dropped if the target object no longer exists.
Offline user's ops conflict with online changesOffline ops are replayed in order after reconnect. Since they carry the original timestamps, the server's LWW rule naturally positions them. For major conflicts a "restore" can be used.
Causality trackingEvery op includes a Vector Clock {userId: lamportClock}. The receiving client takes the element-wise max when applying remote ops, ensuring happens-before relationships are preserved.

13. Viva Q&A

Q1: Why did you choose WebSockets over HTTP polling?
WebSockets maintain a persistent, full-duplex TCP connection, giving sub-100ms latency for drawing operations. HTTP polling introduces 1–2 s delays and wastes bandwidth. Socket.IO adds reconnection logic, rooms, and namespaces on top of raw WebSockets.
Q2: How does your offline sync avoid data loss?
Every drawing operation is written to IndexedDB atomically before being emitted to the socket. On reconnect the client reads the queue in chronological order and replays each op. If the socket disconnects mid-replay, the remaining ops are still in the queue and will be retried next time.
Q3: What is a vector clock and why use it?
A vector clock is a map of {userId → lamport counter} that tracks causality across distributed nodes. Unlike wall-clock timestamps (which can skew), vector clocks tell us definitively whether event A happened-before event B, or whether they are concurrent. We use them to make conflict decisions more accurate than pure timestamp comparison.
Q4: How does role-based access control work?
The requireRoomRole middleware reads the room document from MongoDB, finds the calling user in room.members, and checks their role rank (owner=3, editor=2, viewer=1) against the required minimum. This is enforced on every mutating API route and on the socket (only editors can emit draw operations).
Q5: Why Redis? Can the app run without it?
Redis serves two purposes: (1) Socket.IO Redis Adapter broadcasts events across multiple Node.js instances for horizontal scaling; (2) a per-room op counter triggers auto-saves. If Redis is unavailable the code falls back gracefully — Socket.IO uses in-memory adapter (single-instance only) and auto-saves are skipped.
Q6: What is Fabric.js and why not a raw Canvas API?
Fabric.js is an OOP wrapper over the HTML5 Canvas API. It provides object model (each shape is a JS object with properties), selection handles, serialisation to/from JSON, free-drawing brushes, and event hooks (object:added, object:modified). This serialisation is essential for broadcasting and storing operations.
Q7: How do you prevent password exposure in API responses?
The Mongoose schema sets select: false on the password field, so it's excluded from all queries by default. Additionally the toJSON transform deletes the field before serialisation. The only time we explicitly .select('+password') is during login to run bcrypt comparison.
Q8: How would you scale this to 10,000 concurrent users?
Add more Node.js instances behind a load balancer — Socket.IO Redis Adapter already handles cross-instance event delivery. Use MongoDB Atlas sharding for the database tier. Move large canvasData blobs to S3/R2 and store only a URL in MongoDB. Add a CDN for static assets. Rate-limit per room to throttle cursor spam.
